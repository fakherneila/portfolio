# Comment j'ai construit un portail de production avec 198 tests et 99 Lighthouse

## Le problème

L’équipe RH d’IJSchool coordonnait l’intégration des formateurs entre Notion, Google Forms et Airtable. Les informations étaient dispersées, les rapports manuels et chaque nouveau formateur devait comprendre une partie différente du parcours. Il fallait une interface unique, calme et lisible.

<Callout type="info" title="La vraie contrainte">
L’objectif n’était pas de créer la plateforme la plus complexe, mais de supprimer les frictions d’un flux déjà utilisé chaque semaine.
</Callout>

## Les contraintes

- Environ 100 formateurs allaient utiliser le portail, parfois avec peu d’aisance numérique.
- Le produit devait remplacer un site Notion à l’identique, avec une meilleure expérience.
- J’étais seul développeur, avec huit semaines et aucune base de code existante.
- La sécurité devait couvrir CSRF, limitation de débit, XSS et en-têtes sécurisés.
- La livraison devait inclure de vrais tests automatisés.

## Le choix technique

J’ai choisi React 18, Vite et Tailwind côté client, avec Airtable comme backend-as-a-service. Un backend sur mesure aurait donné davantage de contrôle, mais l’équipe RH utilisait déjà Airtable, son API était documentée et cette décision supprimait l’infrastructure à maintenir dans un projet solo de huit semaines.

La frontière Airtable restait isolée et les lectures étaient mises en cache pendant cinq minutes :

```ts
type AirtablePage<T> = {
  records: Array<{ id: string; fields: T }>
  offset?: string
}

const cache = new Map<string, { expires: number; value: unknown }>()

export async function fetchTable<T>(table: string): Promise<T[]> {
  const cached = cache.get(table)
  if (cached && cached.expires > Date.now()) return cached.value as T[]
  const response = await fetch(`/api/airtable/${table}`)
  if (!response.ok) throw new Error('La requête Airtable a échoué')
  const page = await response.json() as AirtablePage<T>
  const value = page.records.map((record) => record.fields)
  cache.set(table, { expires: Date.now() + 5 * 60_000, value })
  return value
}
```

<Callout type="tip" title="Une frontière simple vaut mieux">
L’interface ne devrait pas savoir si les données viennent d’Airtable, d’une base SQL ou d’un fixture. Un adaptateur étroit rend ce choix remplaçable.
</Callout>

## La stratégie de tests

La suite finale comptait 198 tests unitaires avec Vitest et Testing Library, ainsi que 32 tests end-to-end avec Playwright. La couverture atteignait 78 %. J’ai testé la validation, les états de chargement, les permissions, les états vides et les parcours formateurs les plus importants. En revanche, chaque détail visuel n’avait pas besoin d’un snapshot.

Le générateur de token CSRF gardait un contrat volontairement petit :

```ts
import { describe, expect, it } from 'vitest'
import { createCsrfToken } from './csrf'

describe('createCsrfToken', () => {
  it('retourne une expiration d’une heure', () => {
    const token = createCsrfToken(Date.now())
    expect(token.value).toHaveLength(64)
    expect(token.expiresAt).toBe(Date.now() + 60 * 60 * 1000)
  })
})
```

## La couche de sécurité

Les tokens CSRF expiraient après une heure. La limitation de débit plafonnait les requêtes à dix par minute. DOMPurify nettoyait les chaînes contrôlées par l’utilisateur avant affichage, car un outil interne doit lui aussi traiter ses utilisateurs comme des utilisateurs réels. Enfin, les en-têtes de sécurité réduisaient l’impact d’une mauvaise configuration.

<Callout type="warn" title="La sécurité fait partie de la fonctionnalité">
Une interface élégante qui expose des données ou accepte du HTML dangereux n’est pas terminée. Les contrôles de sécurité doivent faire partie des critères d’acceptation.
</Callout>

## Résultats

Le portail a été déployé sur [ijschool.fr/portail-formateur](https://ijschool.fr/portail-formateur). Lighthouse a atteint 99 en performance, 95 en accessibilité, 100 en bonnes pratiques et 100 en SEO. Environ 100 formateurs l’ont utilisé, les appels API ont diminué de 70 % grâce au cache de cinq minutes et le projet a dépassé 51 commits.

## Ce que je changerais

J’utiliserais un vrai backend pour les transactions atomiques, j’ajouterais axe-core pour les tests d’accessibilité et je mettrais en place la CI/CD dès le premier jour. Airtable était le bon choix dans ces contraintes, mais ne doit pas devenir une excuse permanente lorsque les garanties de cohérence deviennent essentielles.

## Conclusion

Livrer à de vrais utilisateurs rend les retours plus honnêtes. La meilleure architecture était celle qui clarifiait la prochaine action d’un formateur, rendait les erreurs visibles et laissait assez d’espace pour évoluer sans tout réécrire.
